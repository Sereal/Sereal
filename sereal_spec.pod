=head1 NAME

Sereal - Protocol definition

=head1 SYNOPSIS

This document describes the format and encoding of a Sereal data packet.

=head1 VERSION

This is the Sereal specification version 6.01.

The integer part of the document version corresponds to
the Sereal protocol version. For details on incompatible changes between
major protocol versions, see the L</"PROTOCOL CHANGES"> below.

=head1 DESCRIPTION

A serialized structure is converted into a "document". A document is made
up of two parts, the document header and the document body.

=head2 General Points

=head3 Strictness

A compliant Sereal decoder must detect invalid documents and handle them
as a safe exception in the respective implementation language.
That is to say, without a crash or worse.

Invalid documents include, among other things, truncated input, lengths or
offsets that point outside the document, tags that are not defined for the
document's protocol version, reserved tags, unknown extended-tag IDs, and
structural violations such as the COPY, ALIAS and aggregate rules described
below. A decoder must bounds-check every length and offset before using it.

=head3 Little Endian

All numeric data is in little endian format.

=head3 IEEE Floats

Floating points types are in IEEE format.

=head3 Varints

Heavy use is made of a variable length integer encoding commonly called
a "varint" (Google calls it a Varint128). This encoding uses the high bit
of each byte to signal there is another byte worth of data coming, and the
last byte always having the high bit off. The data is in little endian
order with the low seven bits in the first byte, and the next 7 in the
next etc.

See L<Google's description|https://developers.google.com/protocol-buffers/docs/encoding#varints>.

=head2 Document Header Format

A header consists of multiple components:

   <MAGIC> <VERSION-TYPE> <HEADER-SUFFIX-SIZE> <OPT-SUFFIX>

=head3 MAGIC

A "magic string" that identifies a document as being in the Sereal format.
In protocol version 1 and 2, the value of this string is "=srl",
and when decoded as an unsigned 32 bit integer on a little endian machine
has a value of 0x6C72733D. Version 1 and 2 of the protocol require this
magic string.

In protocol version 3 and higher the magic string has been changed to
"=\xF3rl", where \xF3 is "s" with the high bit set. The little endian integer
form of this string is 0x6C72F33D. Having a hight bit set in the magic string
makes it easy to detect when a Sereal document has been accidentally UTF-8
encoded because the \xF3 is translated to \xC3\xB3.

Decoders are required to support the magic string associated to the protocol
versions they can decode, so a decoder that handles protocol versions 1
through 6 must accept both magic strings, and must accept each one only with
the protocol versions it belongs to.

It is an error to use a new magic header on a v1 or v2 packet, and it is
an error to use the old magic header in v3 or later.

=head3 VERSION-TYPE

A single byte, of which the high 4 bits are used to represent the "type"
of the document, and the low 4 bits used to represent the version of the
Sereal protocol the document complies with.

The currently defined protocol versions are 1 through 6. The low four bits
contain the version number. The high four bits select the document encoding.
Protocol version 6 reserves the high bit of this type field to indicate a
keyed checksum envelope; the protected type is 8 plus the corresponding
unprotected type (0 through 4).

The unprotected base types are:

=over 4

=item Z<>0

Raw Sereal format. The data can be processed verbatim.

=item Z<>1

B<This is not a valid document type for Sereal protocol version 2 and up!>

In Sereal protocol version 1, this used to be
"Compressed Sereal format, using Google's Snappy compression internally."
It has long been advised to prefer I<2>, "incremental-decoding-enabled
compressed Sereal," wherever possible. The payload is a Snappy blob without
a length prefix, extending to the end of the document. Protocol version 6
accepts the keyed-checksum form of this type (type 9) because the checksum
envelope supplies the missing length; see below.

=item Z<>2

Compressed Sereal format, using Google's Snappy compression internally as
format I<1>, but supporting incremental-parsing. Long preferred over
I<1> as this is considered a bug fix in the Snappy compression support.

The format is:

  <Varint><Snappy Blob>

where the varint signifies the length of the Snappy-compressed blob
following it. See L</"NOTES ON IMPLEMENTATION"> below for a discussion on
how to implement this efficiently.

=item Z<>3

Compressed Sereal format, using zlib compression. This does similar framing
as the incremental Snappy compression (2):

  <Varint><Varint><Zlib Blob>

where the first varint indicates the length of the uncompressed document,
the second varint indicates the length of the compressed document.
See L</"NOTES ON IMPLEMENTATION"> below for a discussion on
how to implement this efficiently.

This compression format is new in v3 of the specification.

=item Z<>4

Compressed Sereal format, using Zstandard compression internally as
format I<4>.

The format is:

  <Varint><Zstd Blob>

where the varint signifies the length of the zstd-compressed blob
following it. See L</"NOTES ON IMPLEMENTATION"> below for a discussion on
how to implement this efficiently.

The Zstandard frame MUST include C<Frame_Content_Size>, the uncompressed
body length. Decoders may require this size to allocate their output buffer.
Encoders must include it even for small bodies when compression is forced.

This compression format is new in v4 of the specification.

=item Z<>5

Reserved for future use. No document type 5 compression format is defined.

=item Z<>6

Reserved for future use. No document type 6 compression format is defined.

=item Z<>7

Reserved for future use. No document type 7 compression format is defined.

=back

For protocol version 6, types 8 through 12 are the keyed-checksum forms of
base types 0 through 4, respectively. Their payload encoding and compression
framing are identical to the corresponding base type.
The protected form of base type 1 is valid in protocol version 6; its payload
extent is delimited by the checksum envelope length.

Types 5 through 7 and 13 through 15 are reserved for future use. A decoder
encountering a reserved type must reject the document.

=head4 Keyed checksum envelope (protocol version 6)

The checksum type bit indicates that the following envelope occurs after the
optional header suffix and before any compression-specific framing or body:

  <CHECKSUM-TYPE-U8> <CHECKSUM-LENGTH-VARINT> <CHECKSUM>
  <PAYLOAD-LENGTH-VARINT> <PAYLOAD>

Checksum type 0 specifies SipHash-2-4 with a 16-byte secret key and a
64-bit output. The tag is the unsigned 64-bit little-endian SipHash output.
Checksum type 1 specifies SipHash-2-4-128 and checksum type 2 specifies
SipHash-3-6-128, both with a 16-byte secret key and a 128-bit output. Their tags
are two consecutive unsigned 64-bit little-endian words, using the SipHash-128
initialization and finalization convention (C<v1 ^= 0xee> after loading the
key, then C<v2 ^= 0xee> before the first and C<v1 ^= 0xdd> before the second
finalization). In SipHash-c-d, c is the number
of compression rounds per message block and d is the number of rounds in
each finalization stage. Thus 2-4 and 3-6 specify round counts, independently
of the 64- or 128-bit tag size. See the authors'
L<SipHash variant documentation|https://github.com/veorq/SipHash#variants>.
All other checksum types are reserved. Implementations refer to the checksum
type as the checksum I<version> in their option names (for example
C<checksum_v2_key>); the numbering is the same.

The checksum length and payload length are unsigned varints. The checksum
length is the number of bytes in the checksum field. Type 0 requires 8 bytes;
types 1 and 2 require 16 bytes. The payload length is the number of bytes in
the encoded payload following its length field, including any
compression-specific framing. It must cover the payload exactly: a decoder
that finishes the body, or its compression framing, at any other position
must reject the document.

The SipHash input is the complete packet from MAGIC through the checksum type
and checksum-length varint, followed by the payload-length varint and the
complete encoded payload. The checksum field itself is omitted from the
SipHash input. Encoders may initially write zeroes in the checksum field and
fill it after writing the lengths and payload. This covers the header,
optional header suffix (including any user meta data), checksum type, both
lengths, compression framing, and payload. Decoders that verify the checksum
must do so before interpreting the header suffix, before processing
compression framing and before decompressing the payload.

Decoders must bounds-check both lengths before skipping or reading their
corresponding fields. An unknown checksum type can be skipped using its
checksum-length varint when the decoder's checksum policy allows it; a decoder
cannot verify such a checksum. A decoder's default policy may warn and decode
without authentication when no matching key is configured. Implementations
may provide a policy that instead rejects such packets, or explicitly ignores
checksum authentication. Supplying a key does not require packets to be
protected; unprotected packet types remain valid.

The Perl, Go and Java implementations share the following policy names and
semantics. They are not part of the wire format, but new implementations are
encouraged to offer the same choices:

=over 4

=item verify-if-available

The default. Verify when a key for the packet's checksum type is configured;
otherwise warn and decode without authentication. Unprotected packets are
accepted.

=item die

Verify, and reject a protected packet whose checksum type is unsupported,
whose key is not configured, or whose tag does not match. Unprotected packets
are accepted.

=item require_key

As C<die>, and additionally reject unprotected packets. A key must be
configured when the decoder (or encoder) is created.

=item ignore, ignore-warn

Skip verification. The envelope framing is still validated. C<ignore-warn>
emits a warning for every protected packet.

=back

A checksum mismatch is always an error when the tag is verified.

This is a keyed integrity check, not encryption. Type 0 has a 64-bit tag;
types 1 and 2 have 128-bit tags. The key is never written to the document.

=head4 Key preparation (informative)

The key is 16 raw bytes. So that keys derived from the same secret agree
across implementations, Perl (C<prepare_checksum_key>), Go
(C<PrepareChecksumKey>) and Java (C<SerealChecksum.prepareKey>) derive a key
from an arbitrary-length secret C<KEY> and an optional second secret
C<OPT_KEY> (empty by default) as:

  K1  = SipHash-2-4-128( key = "Call me Ishmael.",
                         msg = "Out damned spot!" . OPT_KEY )
  OUT = SipHash-2-4-128( key = K1,
                         msg = "Luke, I am your father." . KEY )

Both SipHash outputs use the 128-bit convention described above and are
taken as 16 little-endian bytes. This is a normalization step that produces
the required key size; it does not add entropy and is not a substitute for a
password-based key derivation function.

=head3 HEADER-SUFFIX-SIZE

The structure of the header includes support for embedding additional data.
This is accomplished by specifying the length of the suffix
in the header with a varint. Headers with no suffix will set this to a
binary 0. This is intended for future format extensions that retain some
level of compatibility for old decoders (which know how to skip the
extended header due to the embedded length).

=head3 OPT-SUFFIX

The suffix may contain whatever data the encoder wishes to embed in the
header. In version 1 of the protocol the decoder never looked inside
this data. Later versions may introduce additional rules for this field.
Starting from version 2 of the protocol, this variable-length part of the header
may be empty or have the following format:

    <8bit-BITFIELD> <OPT-USER-META-DATA>

=over 2

=item 8bit-BITFIELD

If not present, all bits are assumed off. In protocol version 2 and later,
only the least significant bit is defined: If set, the bitfield is
followed by the C<E<lt>USER-META-DATAE<gt>>. If not set, there is
no user meta data. The remaining seven bits are reserved. Encoders must
leave them clear and decoders ignore them.

=item OPT-USER-META-DATA

If the least significant bit of the preceding bitfield is set, this
may be an arbitrary Sereal document body. Like any other Sereal
document body, it is self-contained and can be deserialized independently
from any other document bodies in the Sereal document. This document
body is NEVER compressed. It is decoded with the rules of the document's
protocol version, its offsets are relative to its own start, and in a
checksummed document it is covered by the checksum.

This is intended for embedding small amounts of meta data, such as
routing information, in a document that allows users to avoid
deserializing very large document bodies needlessly or having to
call into decompression logic.

=back

=head2 Document Body Format

The body is made up of tagged data items:

    <TAG> <OPT-DATA>

Tagged items can be containers that hold other tagged items.
At the top level, the body holds only ONE tagged item (often
a reference to an array or hash) that holds others.

The ARRAY and HASH tags describe an aggregate rather than a value. They are
valid only as the item immediately following a REFN tag (PAD bytes may
intervene, and the aggregate tag may carry the track flag); the compact
ARRAYREF and HASHREF tags include the reference. A bare ARRAY or HASH tag
anywhere else, including at the top level of a body, as an array element,
hash value, class name, or COPY target, is invalid.

=head3 TAG

A tag is a single byte which specifies the type of the data being decoded.

The high bit of each tag is used to signal to the decoder that the
deserialized data needs to be stored and tracked and will be reused again
elsewhere in the serialization. This is sometimes called the "track flag"
or the "F-bit" in code and documentation. Its status should be ignored
when processing a tag, meaning code should mask off the high bit and
only use the low 7 bits.

Some tags, such as POS, NEG and SHORT_BINARY contain embedded in them
either the data (in the case of POS and NEG) or the length of the
OPT-DATA section (in the case of SHORT_BINARY).

=head3 OPT-DATA

This field may contain an arbitrary set of bytes, either determined
implicitly by the tag (such as for FLOAT), explicitly in the tag (as in
SHORT_BINARY) or in a varint following the tag (such as for STRING).

When referring to an offset below, what's meant is a varint encoded
absolute integer byte position in the document body.
That is, an offset of 10 refers to the
tenth byte in the Sereal document body (ie. excluding its header).
Sereal version 1 used to mandate offsets from the start of the document
header.

=head3 Integers

Integers from 0 to 15 are encoded in the POS tags and integers from -16
to -1 in the NEG tags, with no payload. VARINT carries an unsigned integer
as a varint. ZIGZAG carries a signed integer as a zigzag-encoded varint
(C<<< (n << 1) ^ (n >> 63) >>> for a 64-bit value, with an arithmetic right
shift) and is valid in every protocol version. NEG_VARINT, new in protocol
version 6, carries a negative integer as a varint holding its absolute
value; the magnitude must not be zero. Encoders producing protocol version 6
use NEG_VARINT for integers below -16, and ZIGZAG for them in protocol
version 5 and earlier. Decoders accept both in protocol version 6 documents.

The reference implementations represent integers as 64-bit values. A decoder
may reject a varint, zigzag or magnitude that does not fit its native
integer range; the Perl, Go and Java decoders accept NEG_VARINT magnitudes
up to 2**63 inclusive.

=head3 Floating Point

FLOAT is followed by a 4-byte IEEE 754 binary32 value and DOUBLE by an 8-byte
IEEE 754 binary64 value, both little endian. FLOAT_128, new in protocol
version 5, is followed by a 16-byte IEEE 754 binary128 value (the quadmath
C<__float128> type), little endian. Decoders without native support for the
type may expose the raw bytes or reject the value; the Go and Java decoders
return the 16 bytes unchanged.

LONG_DOUBLE is followed by the encoder platform's native C<long double>, in
its native size and layout: 16 bytes on most 64-bit platforms, where x86 uses
80-bit extended precision followed by six zero bytes, and 8 or 12 bytes on
some others. Only the Perl implementation reads and writes it, and only
between platforms with the same C<long double>. Encoders that need
portability should use DOUBLE (see the Perl encoder's C<use_standard_double>
option) or FLOAT_128.

=head3 Booleans

FALSE and TRUE, present since protocol version 1, have no payload and
represent Perl's immortal boolean values C<PL_sv_no> and C<PL_sv_yes>.
NO and YES, new in protocol version 5, represent the distinct boolean type
introduced in Perl 5.36 (values for which C<SvIsBOOL()> is true). In Perl
both pairs decode to the same values, C<PL_sv_no> and C<PL_sv_yes>. Other
languages map all four tags to their native false and true. NO and YES are
only valid in protocol version 5 and later documents.

=head3 Extended Tags

EXTEND is followed by a one-byte extended-tag ID that selects the actual tag,
and then by that tag's payload. EXTEND is only valid in protocol version 6
and later documents. The defined IDs are:

      ID | Name           | Follow
    -----+----------------+---------------------------------------------
    0x26 | VSTRING-BINARY | <LEN-VARINT> <SPELLING> - v-string, binary
    0x27 | VSTRING-UTF8   | <LEN-VARINT> <SPELLING> - v-string, UTF-8
    0xff | UNDEF_DEADLY   | none - decode as undef by default; never encode

All other IDs are reserved. Because the payload of an unknown ID cannot be
skipped, a decoder must reject a document containing one. See
L</"Protocol Version 6"> for the semantics of these tags.

=head3 Reserved Tags

RESERVED_0 and RESERVED_1 have no defined payload and must not appear in a
document; decoders reject them. PACKET_START is not a body tag: it is the
first byte of the magic string and is listed so that a header can never be
mistaken for a body tag.

=head3 The Track Bit And Cyclic Data Structures

The protocol uses a combination of the offset of a tracked tag and the
flag bit to be able to encode and reconstruct cyclic structures in a single
pass.

An encoder must track duplicated items and generate the appropriate ALIAS or
REFP tags to reconstruct them, and when it does so ensure that the high
bit of the original tag has been set.

When a decoder encounters a tag with its flag set it will remember the
offset of the tag in the output packet and the item that was decoded from
that tag. At a later point in the packet there may be an ALIAS or REFP
instruction which will refer to the item by its offset, and the decoder
will reuse it as needed.

=head3 The COPY Tag

Sometimes it is convenient to be able to reuse a previously emitted
sequence in the packet to reduce duplication. For instance a data
structure with many hashes with the same keys. The COPY tag is used for
this. Its argument is a varint which is the offset of a previously
emitted tag, and decoders are to behave as though the tag it references
was inserted into the packet stream as a replacement for the COPY tag.

COPY does not require the referenced item to have its track flag set: the
decoder can reread the tag from its location alone. The COPY tag itself may
have its track flag set so that later ALIAS tags can refer to the newly
created value at the COPY offset. Rereading a COPY source must not register
new alias targets at source offsets or replace the values already tracked
at those offsets.

ALIAS replaces a value slot in an array or hash. It cannot be used as the
immediate referent of REFN. To create a new scalar referent with the contents
of an earlier string, an encoder can use REFN followed by COPY; REFP instead
creates a reference to an existing tracked value.

COPY tags are forbidden from referring to another COPY tag, and are also
forbidden from referring to anything containing a COPY tag, with the
exception that a COPY tag used as a value may refer to an tag that uses
a COPY tag for a classname or hash key.

=head3 String Types

Sereal supports three string representations. Two are "encodingless" and
are SHORT_BINARY and BINARY, where binary means "raw bytes". The other
is STR_UTF8 which is expected to contain valid canonical UTF8 encoded
unicode text data. Under normal circumstances a decoder is not expected
to validate that this is actually the case, and is allowed to simply
extract the data verbatim.

SHORT_BINARY stores the length of the string in the tag itself and is used
for strings of less than 32 characters long. Both BINARY and STR_UTF8
use a varint to indicate the number of B<bytes> (octets) in the string.

Note that the use of the term "BINARY" simply means that we do not know
what encoding the data uses, it does not imply that such data is B<not>
text, nor does STR_UTF8 imply that the data B<is> text (although it is
likely).

What STR_UTF8 B<does> imply that the data is encoded using the
rules for encoding C<utf8>, which is similar but subtly distinct from
true C<UTF-8>. The main distinction between the two is that Perls
C<utf8> can be used to represent a wider range of codepoints than
C<UTF-8>, including codepoints that are forbidden in C<UTF-8>, such as
codepoints C<U+D800> through C<U+DFFF> inclusive (which are used ONLY in
C<UTF-16>), and codepoints larger than C<U+10FFFF> which is the maximum
allowable Unicode codepoint.

Sereal does NOT validate that such STR_UTF8 strings *are* correctly encoded
as it trusts Perl to do the right thing. When implementing Sereal in other
languages it is up to the implementor how to handle these illegal
codepoints, we do not expect such data to reliably round trip between
Perl and another language as some languages, eg Javascript cannot properly
handle such data. It is extremely rare to see code that actually makes
use of such codepoints, and Perl will not do so on its own.

Protocol version 6 adds a fourth, special-purpose string representation for
Perl v-strings as extended tags. See L</"Protocol Version 6">.

=head3 Hash Keys

Hash keys are always one of the string types, or a COPY tag referencing a
string.

Hash keys MUST NOT be encoded as ALIAS tags or used as ALIAS targets. A key
identifies an entry by its string contents; it is not an aliasable value slot.
Keys may reuse strings from earlier keys or values using COPY, and values may
also use COPY to reuse an earlier key string.

When a value is encoded as COPY of a key string, decoding it creates a value
which can subsequently be aliased. The encoder may set TRACK_FLAG on that
COPY tag and use ALIAS tags referring to the value's COPY offset. Those ALIAS
tags refer to the value, not to the original key. As with all COPY tags, the
COPY itself must refer directly to a string definition, never to another COPY
tag. Encoders that deduplicate both keys and values must distinguish reusable
string definitions from aliasable values.

=head3 Handling Objects

Objects are serialized as a class name and a tag which represents the
objects data. In Perl land this will always be a reference. Mapping Perl
objects to other languages is left to the future, but the OBJECT_FREEZE
and OBJECTV_FREEZE tags provide a basic method of doing that, see below.

Note that classnames MUST be a string, or a COPY tag referencing a string.

OBJECTV varints MUST reference a previously used classname, and not an
arbitrary string.

Sereal implementations may choose to allow authors of classes to provide
hooks for custom object serialization. Depending on the Sereal
implementation, this feature may require enabling with an encoder
option on the encoding side, but compliant decoders must
at least recognize the OBJECT_FREEZE and OBJECTV_FREEZE tags. The
interface shall be such that if enabled in the encoder, for each
object in the input that has a C<FREEZE> method, the encoder will invoke
said C<FREEZE> method on the object and pass in the string C<Sereal>
to allow distinguishing from other serializers (this is inspired by
the C<CBOR::XS> CBOR implementation). If there is no C<FREEZE> method
available, then a normal OBJECT or OBJECTV tag is emitted, serializing
the object content deeply. If invoked, the C<FREEZE> method must return
a list of data structures that are serializable by Sereal. The encoder
shall emit an OBJECT_FREEZE or OBJECTV_FREEZE tag followed by a reference
(REFN) to an array (ARRAY) of the Sereal-encoded data structures that
were returned from C<FREEZE>.

Upon decoding OBJECT_FREEZE or OBJECTV_FREEZE, a compliant decoder
(unless explicitly instructed not to) will invoke the C<THAW>
class method of the given class. (Likely, implementations should
throw a fatal error if no such method exists for a class referenced
by OBJECT(V)_FREEZE.) Arguments to that method will be the string
C<Sereal> as first argument, and then the decoded data structures
that were returned from the C<FREEZE> call.
The return value of that C<THAW> call needs
to be included in the final output structure. See the documentation
of the Perl Sereal implemenation for examples of FREEZE/THAW methods.

=head3 Dealing with undefined values

The concept of undef is a little tricky in Perl. A variable may be
undefined, in addition there is also a definitive "undef" which Perl
uses in many situations. This definitive "undef" is a globally shared,
immutable value. Its use is vaguely equivalent to aliasing the same,
read-only copy of a Perl value that happens to be undefined.

The difference can be illustrated with the following code:

    my $x;
    print +(\$x    == \$x)     ? "same" : "different", "\n";
    print +(\undef == \undef)  ? "same" : "different", "\n";
    print +(\$x    == \undef)  ? "same" : "different", "\n";

which should print out

    same
    same
    different

In protocol versions 1 and 2 it was not possible to represent both forms
of undef correctly, and Sereal defaulted to the "undefined variable"
interpretation represented by the UNDEF tag in most situations.

As of protocol version 3 the CANONICAL_UNDEF tag is used to handle this special
case of undef so that Perl data structures can round trip properly.
Other languages are free to treat CANONICAL_UNDEF and UNDEF as is appropriate
to their language semantics:
If there is an equivalent to this globally shared undefined value (PL_sv_undef in Perl's
implementation) then they should map CANONICAL_UNDEF
accordingly, otherwise they are free to treat CANONICAL_UNDEF the same as UNDEF.

=head1 PROTOCOL CHANGES

=head2 Protocol Version 6

Protocol version 6 adds the NEG_VARINT tag, the EXTEND tag with its three
defined extended-tag IDs, and the keyed checksum envelope. NEG_VARINT and
EXTEND are only valid in protocol version 6 and later documents; decoders
reject them in older documents.

=head3 NEG_VARINT

The NEG_VARINT tag encodes a negative integer as the tag followed by a varint
containing the integer's absolute value. The magnitude must be nonzero. In
protocol version 6 and later, encoders use NEG_VARINT for integers below -16;
the compact NEG tags continue to represent -1 through -16. Encoders producing
protocol version 5 or earlier continue to use ZIGZAG for these larger negative
integers. Decoders must accept ZIGZAG in every protocol version, including
version 6, for compatibility with older encoders.

=head3 UNDEF_DEADLY

Protocol version 6 reserves extended-tag ID 255 (C<0xff>) for
C<UNDEF_DEADLY>, encoded as C<EXTEND 255> (bytes C<3e ff>), with no payload.
It is intended primarily for testing decoder behavior and diagnostics; normal
Sereal data should not contain it.
Decoders MUST treat this value as an ordinary undef by default. A decoder
may offer an C<undef_deadly_policy> setting: C<undef> silently decodes it as
undef, C<warn> warns on each encounter and decodes it as undef, and C<die>
rejects the document with an exception.

A compliant encoder MUST NOT emit C<UNDEF_DEADLY> as a value tag. It is a
diagnostic sentinel, not a terminator, and MUST NOT be appended to encoded
documents. Concatenated documents retain their existing framing. The same
bytes occurring inside a string or compressed payload are ordinary data,
not an encounter with this tag. Extended-tag ID 0 is unassigned.

=head3 VSTRING-BINARY and VSTRING-UTF8

Protocol version 6 adds extended tags C<VSTRING-BINARY> and C<VSTRING-UTF8>
for Perl v-strings (version literals such as C<v1.2.3> or C<65.66.67>). They
are encoded as EXTEND followed by the corresponding extended-tag ID (0x26,
the BINARY tag value, or 0x27, the STR_UTF8 tag value), then a length varint
and the original v-string spelling. The spelling is the sole payload: a
decoder reconstructs the string value from it, and Perl additionally keeps
the spelling as the string's v-string magic.

The spelling must be non-empty and must match

  ^v?[0-9_]*(\.[0-9][0-9_]*)*$

that is, an optional leading C<v>, then dot-separated components, where
every component after a dot starts with a digit. Each component's value is
its decimal digits with underscores ignored, read as an unsigned 64-bit
integer with wraparound; an empty first component has the value zero. The
reconstructed string has one character per component, with that
component's value as its code point. VSTRING-UTF8 is used when any
component is greater than 127, since the string then needs UTF-8 encoding;
VSTRING-BINARY is used otherwise. In Perl terms, the ID tells whether the
reconstructed PV is UTF-8 flagged. Decoders reject an empty spelling, a
spelling that does not match the grammar, and an ID that does not match
the components.

Languages without a v-string type may carry the spelling as a string; the
Go and Java implementations provide a dedicated v-string type that
preserves it.

=head3 Keyed checksums

Protocol version 6 also defines keyed checksum types 8 through 12, the
checksum envelope and checksum types 0 through 2. See
L</"Keyed checksum envelope (protocol version 6)"> for the envelope layout
and verification rules.

=head2 Protocol Version 5

Protocol version 5 adds the NO and YES tags for Perl's distinct boolean values
(C<PL_No> and C<PL_Yes>), available in Perl 5.36 and later. These correspond to
JSON false and true, respectively, and have no payload. See L</"Booleans">.

The FLOAT_128 tag is also added for the quadmath C<__float128> value type; it
is followed by the 16-byte little-endian IEEE 754 binary128 value. Decoders
without native quadmath support may expose the raw bytes or reject the value.
See L</"Floating Point">.

NO, YES and FLOAT_128 are only valid in protocol version 5 and later
documents.

=head2 Protocol Version 4

"zstd" compression (document type 4) support is added. As detailed above, its
structure is

  <Varint><Zstd Blob>

where the varint indicates the length of the compressed document.

=head2 Protocol Version 3

In Sereal protocol version 3, the magic string has been changed to make it
easier to detect UTF-8 encoded data by setting the high bit on the 's'
character, thus changing the older "=srl" to "=\xF3rl". Encoders generating
version 3 of the protocol or later must use the new header, and encoders
generating version 1 or 2 of the protocol must use the old header.

Also new is the "zlib" compression (document type 3). As detailed above, its
structure is

  <Varint><Varint><Zlib Blob>

where the first varint indicates the length of the uncompressed document,
the second varint indicates the length of the compressed document.

Additionally there is the new CANONICAL_UNDEF tag, used to represent Perl's
canonical, shared undefined value (PL_sv_undef) in certain edge cases.
See L</"Dealing with undefined values"> for details.

=head2 Protocol Version 2

In Sereal protocol version 2, offsets were changed from being relative to
the start of the document (including header) to being relative to the start
of the document body (ie. excluding the document header). This means that
Sereal document bodies are now self-contained - relocatable within the document.
Note that the offset is 1-based, which means that to point the first byte
of the body its value must be 1.

Additionally, protocol version 2 introduced the 8bit bit-field (8bit-BITFIELD)
in the variable-length/optional header part (OPT-SUFFIX) of the document
and the user-meta-data section (OPT-USER-META-DATA) of the variable-length header.

Protocol version 2 introduces the OBJECT_FREEZE and OBJECTV_FREEZE tags in
place of two previously reserved tags. The meaning and implementation of these
two tags is described in the L</"Handling Objects"> section of this document.
In a nutshell, it allows application developers to have custom hooks for
serializing and deserializing the instances of their classes.

=head1 NOTES ON IMPLEMENTATION

=head2 Encoding the Length of Compressed Documents

With Sereal body format type 2 (see above), you need to encode (as a varint)
the length of the Snappy-compressed document as a prefix to the document body.
This is somewhat tricky to do efficiently since at first sight,
the amount of space required to encode a varint depends on the size of the
output. This means that you need to do the normal Sereal-encoding of the
document body, then compress the output of that, then append the varint
encoded length of the compressed data to a Sereal header, then append the
compressed data. In this naive way of implementing this Snappy compression
support, you may end up having to copy around the entire document up to three
times (and may end up having to allocate 3x the space, too). That is very
inefficient.

There is a better way, though, that's just a tiny bit subtle.
Thankfully, you have an upper bound on the
size of the compressed blob. It's the uncompressed blob plus the size of
the Snappy header (a Snappy library call can tell you what that is in
practice). What you can do is before compressing, you allocate a varint
that is long enough to encode an integer that is big enough to represent
the upper limit on the compressed output size. Then you proceed to
point the compressor into the buffer right after the thusly preallocated
varint. After compression, you'll know the real size of the compressed
blob. Now, you go back to the varint and fill it in. If the reserved
space for the varint is B<larger> than what you actually need, then
thanks to the way varints work, you can simply set the high bit on the
last byte of the varint, and continue to set the high bits of all following
padding bytes B<except the last>, which you set to 0 (NUL). For details
on why that works, please refer to the Google ProtoBuf documentation
referenced earlier. With this specially crafted varint, any normal
varint parsing function will treat it as a single varint and skip right
to the start of the Snappy-compressed blob. The varint is a correct
varint, just not in the canonical form. With this modified plan, you
should only need one extra malloc, and (beyond that which the Snappy
implementation does), no extra, large memcpy operations.

=head1 IMPLEMENTATIONS

The implementations in the Sereal repository supported the following protocol
versions when this revision of the specification was written (October 2026).
This list is informative and will go out of date; the README of each
implementation is authoritative.

=over 4

=item Perl (C<Perl/>)

Reference implementation. Encodes and decodes protocol versions 1 through 6
(default 6) with Snappy, zlib and zstd compression, all three checksum types,
and the LONG_DOUBLE and FLOAT_128 tags where the perl supports them.

=item Go (C<Go/sereal>)

Decodes protocol versions 1 through 6, including all checksum types and the
v-string extended tags. Encodes protocol version 3 by default and version 6
through C<NewEncoderV6()>. Does not decode LONG_DOUBLE; FLOAT_128 is carried
as its raw bytes.

=item Java (C<Java/>)

Decodes protocol versions 1 through 6 in C<Decoder>, C<TokenDecoder> and the
jackson data format, including all checksum types and the v-string extended
tags. Encodes protocol versions 1 through 6 (default 4). Does not decode
LONG_DOUBLE; FLOAT_128 is carried as its raw bytes.

=item Python, Ruby, JavaScript, Objective-C, Erlang

Older ports that predate protocol version 5. They handle the protocol
version 1 to 4 feature set (the Python decoder accepts versions 3 and 4, the
JavaScript decoder up to version 3, Ruby and Objective-C write version 2)
and do not understand the NO, YES, FLOAT_128, NEG_VARINT and EXTEND tags or
the checksum envelope.

=back
